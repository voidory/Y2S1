1. WHAT THIS FILE IS
   A single, self-contained, offline study app for NTU final exams. Open it by double-click. It holds three modules:
     CM2021  Inorganic and Bioinorganic Chemistry (Kinjo Ch 1-5 and Hiang Kwee Ch 6-9)
     CM2011  Analytical Chemistry
     CM2061  Chemistry and Biological Chemistry Laboratory I (lab exam; manual pp.3-51, the 2015 paper as a style reference)
   Everything it needs is inlined: the app code, the question banks and every other content file (as JSON), the
   libraries (Dexie, KaTeX with fonts, Lucide, the Tailwind runtime) and the web fonts. No network request is made.
   Progress is stored per browser in IndexedDB (database managed by Dexie), so a copy given to someone else starts fresh.
   Keep the file at the same path and name when you replace it with a newer build: some browsers key local storage to the file location.
   CM2061 is built in stages. Stages 1 and 2 (this build): framework, techniques, spectroscopy concepts and databook look-ups, all fifteen
   experiments, the calculations, a seed of e-lab 2 (metal chelate), six unseen-procedure case chains (model procedures, not verified
   published ones), and draw-then-reveal structure and apparatus sets, with a 2-hour final-style paper. Still to come: the NMR and IR
   trainers and the other three e-labs. Node ids never change between stages, because the app
   deletes progress for any node that disappears from a bank.

2. FILE LAYOUT (top to bottom)
   a. This comment.
   b. <head>: styles, the content shim (see 3), Tailwind runtime and config, KaTeX, Lucide.
   c. <body>: static shell only: header with the module switch, sidebar (md and up), bottom tab bar (phone), one
      <main id="appRoot"> that every screen renders into, modals and sheets.
   d. One inline <script type="module"> holding the whole application, with Dexie inlined at its start.
      The app is a set of namespaces, each an IIFE (a self-invoking function returning a plain object).
      They are all exposed at the end on window.__MASTERY_ENGINE__ so tests and tools can load them.

3. HOW IT RUNS
   * The app asks for content with fetch('content/<dir>/<file>.json'). The inlined shim (a global FILES map) answers
     those requests from memory, so the same code runs online (from files) and offline (from this file).
   * Boot: open IndexedDB, seed the modules from SEED_MODULES if the stored CONTENT_VERSION is older, add any module or week
     the install lacks (a new module needs no version bump), load every module's bank, skill map and side files, scope them,
     then render the route.
   * State lives in one object, appState. render() redraws the whole active route into #appRoot; there are no
     frameworks. Handlers are attached after each render by the view's bind function.
   * Layout rule, enforced by tests: no page scroll anywhere; the phone uses a step flow and a bottom tab bar.

4. NAMESPACES (in the order they appear)
   Expr        safe expression language for generated numbers (sqrt, log, sigfig, sd ...).
   DB          Dexie database: modules, nodes, attempt logs, review states, settings rows.
   Content     MODULES list (CM2021, CM2011, CM2061), content loaders, out-of-scope filter, focus sets, methods, supersession pairs.
   Scheduler   which question next (probe plus focus allocation, retry queue, cram, coverage, mock recipes, plan).
               FINAL_RECIPES holds one final-style paper per module; the CM2061 entry (40 pick-one questions plus short answers,
               2 hours) is generated by tools/cm2061/recipe.mjs from the bank.
   Mastery     retires skills you have shown you know, measured in card time.
   Review      the answer-review card: what exactly is wrong.
   Figures     slider pictures, microstate/term enumeration (termsOf) and Tanabe-Sugano drawing and solving.
   Naming      (CM2021) coordination-compound nomenclature: ligands, metals, generator, namer, formula parser, grader.
   Trainer     (CM2021) step drills and chained questions for microstates, terms, Tanabe-Sugano and naming.
   Weakness    where marks are being lost and what to do about it.
   Reactions   (CM2021) the reaction list: cards, grading, patterns, exceptions, spaced boxes.
   Evaluators  graders for every answer type (choice, mapped fields, typed equation, rubric, ordered list ...).
   LF          ligand-field engine (oxidation state, dn, geometry, CFSE) used by generators and the answer checks.
   IsomerEngine, Widgets   3D isomer explorer and interactive widgets.
   UI          appState, every screen (study, mock, readiness/plan, bank, settings, reactions, trainer), sheets, keyboard.
   (CM2061 stage 1 adds no namespace: it runs on the shared engines. Its NMR predictor and IR drills will be new Trainer kinds.)

5. DATA MODEL
   Module      { moduleCode, title, examTimestamp, weeks:[{weekNum,title,examWeight}] } seeded from SEED_MODULES.
   Question    node { id, moduleCode, metadata, variants[] }. A variant has stem, inputSlot (choice, mapped_fields,
               typed_short, typed_synthesis, unordered_set, ordered_list, typed_equation, interactive_widget),
               evaluator, optional variables.sampled/derived (values drawn fresh each time the question is served).
               Every CM2061 node names its source in metadata.source (a manual page, the 2015 paper style or a reference).
   Skill map   chunks (topics) of skills, each skill with marks and linked node ids; marks sum to 100 per module.
   Side files  methods (how-to pages), supersedes (harder question covers an easier one), focus sets (cross-topic
               bundles), out-of-scope (chapters, chunks and questions hidden without deleting anything), figures.
   Progress    attempt logs, review states, settings rows (activeModule, plan, savedLater, skippedLater,
               reactionStats, trainerStats ...). Progress is never part of the content, so content can be replaced.

6. CONTENT FILES INLINED HERE (key = path the app fetches)
   content/<dir>/question-bank.json   all questions of a module            (required)
   content/<dir>/skill-map.json       chunks, skills, marks                  (required)
   content/<dir>/methods.json         how-to pages                           (optional)
   content/<dir>/supersedes.json      easier-covered-by-harder pairs         (optional)
   content/<dir>/focus-sets.json      cross-topic skill bundles              (optional)
   content/<dir>/out-of-scope.json    hidden chapters, chunks, questions     (optional)
   content/cm2021/reactions.json      reaction list, patterns, exceptions    (CM2021 only)
   content/figures/ts.json            Tanabe-Sugano curves (shared)
   <dir> is cm2021, cm2011 or cm2061. CM2061 currently ships question-bank.json and skill-map.json only; they are generated
   by tools/cm2061/build.mjs from the files beside it (never hand-edited).

7. ALGORITHM FOR A BUILDER THAT ADDS A NEW MODULE TO THIS FILE (or to the source it was built from)
   Input: a module spec { code, dir, title, weeks[], bank[], skillMap, optional methods, supersedes, focusSets,
          outOfScope, special features } and this file (or index.html plus public/content).
   Output: the same file with the module added and nothing else changed.

   STEP 1  Author the content (never by hand-editing the inlined JSON).
     1.1 Write generators in tools/<dir>/*.mjs. Each emits question nodes; compute every answer with the in-app
         engines (Expr, Figures, LF, Naming) so the key cannot drift from the app. Put mistakes in as named wrong
         routes (paths) and carried-forward credit (ecf). Never print values the exam provides.
     1.2 Give every choice variant inputSlot.shuffleOptions = true (or run the shuffle tool), pin "none/all of the
         above" last, and never cite options by letter in explanations.
     1.3 Build the skill map: chunks, skills, marks (rescale to 100 so weight = marks / 100), each skill linked to
         node ids. Every node must be linked to at least one skill.
     1.4 Optional files: methods (markdown to JSON with real formulas in LaTeX), supersedes (only where the harder
         question truly contains the easier calculation), focus sets, out-of-scope (list the question ids too).
   STEP 2  Register the module in the source (two edits in index.html; a third only if you want to force a re-seed).
     2.1 Content.MODULES: add { code, dir, recordKey }. The recordKey must be unique ('bundledBank:<code>').
     2.2 SEED_MODULES: add { moduleCode, title, examTimestamp, targetRetention, weeks[] }.
     2.3 Bumping CONTENT_VERSION is NOT needed to add a module: boot adds any module or week an install lacks without touching the
         rest. Bump it only to re-seed existing modules. Verify on a browser that already has the old file's progress: attempts
         must survive and the new module must appear (tests/e2e/cm2061.cjs does this on one profile and one origin).
   STEP 3  Wire module-specific screens (only if the module has any).
     3.1 Gate every module-only nav tab with activeModule === '<code>' in updateNavChrome (and in the route reset
         when the module switches), exactly as Reactions and Trainer are gated to CM2021.
     3.2 A new trainer: add kinds to Trainer (KINDS[k] = { group, name, what, ts, tab }), a builder per kind that
         returns { kind, step, prompt, fields|grid|chips, hint, explain, check(answers) -> { ok, want, score, pass } },
         and optionally a chain(id) returning [{kind, ctx}] that share one ctx. The existing screen, stats row and
         tab strip then work unchanged; add a tab key to the home screen only for a new top-level group.
     3.3 A new pure namespace goes above Trainer in the script, must not touch document at load time (the Node test
         sandbox loads the script), and is exported on window.__MASTERY_ENGINE__.
   STEP 4  Validate before bundling.
     4.1 Unit tests load the namespaces in a Node vm sandbox: fuzz every variant over many seeds, check that each
         model answer passes its own evaluator and a blank scores zero, that every wrong route is named, that every
         skill link and supersession ref resolves, and that scope files point only at real ids.
     4.2 Browser tests (Playwright): a question renders and is answered, the module switch changes the bank, the
         layout check shows no page scroll at phone, tablet and laptop widths, no page errors.
     4.3 Factual keys cannot be computed by these engines, so a reader who did not write the items audits a random 25% of the
         factual nodes (and every node of the spectroscopy and case-chain chunks) against the manual or a cited reference;
         fix the errors and re-sample until a sample comes back clean. tools/cm2061/audit.mjs exports a reproducible sample.
   STEP 5  Bundle: node tools/bundle.mjs. It (a) reads index.html, (b) collects every file under public/content into
     the FILES map and inlines it as the fetch shim, (c) inlines Tailwind, fonts, KaTeX, Lucide and Dexie from a
     local cache, (d) fails if any src, href or import still points at the network, (e) writes dist/.
   STEP 6  Verify the artefact offline: open it with all network requests blocked (tests/e2e/standalone.cjs) and
     check every module loads, progress survives a reload, and no request leaves the page.
   STEP 7  Update this comment (tools/standalone-header.txt): add the new module to section 1, its files to section 6 and any new
     namespaces to section 4.

   Rules a builder must keep:
     * Content and progress are separate. Replacing a content file never deletes attempts. Hiding something (scope)
       is done by listing it in out-of-scope.json, never by deleting nodes.
     * Question text is written in the author's own words; course material is used for private study only.
     * Everything a module needs is looked up by moduleCode or dir; no module-specific constant may leak into shared
       code except behind the activeModule gate.
     * The existing modules keep their ids, record keys and file names.

8. KNOWN LIMITS OF THIS BUILD
   Content shown reflects the repository at build time. The Tanabe-Sugano curves are computed from first principles
   with the original per-ion C/B values, so a slide drawn with another C/B differs slightly. Naming drills follow the
   Kwee slide conventions (-o endings, bis/tris for names that already contain a Greek prefix, -ate for anions).
   CM2061: no exam date is set (set it in Settings). The exam is open-databook (the CBC databook, which has no densities: the paper
   supplies those); items cite databook pages and use its ranges. Only one e-lab screen was supplied, without answers, so the e-lab
   items are keyed from standard chemistry and the databook, not the course's key. The databook misprints silicon as 29.0855
   (28.0855), so no item uses silicon. The manual's
   own statements on some points differ from common practice (recovering from too much recrystallisation solvent; "six" NMR
   spectrometers listed as 300, three 400 and 500 MHz); items follow the manual's wording and say so.
